# What changed, how it works, and why

## 1. Why a conversational model was giving the wrong kind of question

The old paper lookup sent paper summaries and a few shortened question samples to the AI.
The complete readable questions lived in frontend JSON files, separate from chatbot retrieval.
An AI can produce plausible practice questions, but that does not establish that they appeared in CDS.
Adding more instructions or training on user chats would not repair this missing data connection.

## 2. One shared question bank

Migration `20260926_14` adds `paper_questions.transcription` and `doubt_messages.pyq_result`.
The importer matches each existing transcription to a database question using its paper-page path
and question number. It validates the four options, paper identity and existence of the source image.
It does not overwrite answer keys, IDs, attempts or legacy source text.

Both the papers page and the tutor now read the same backend transcription. The papers page no
longer downloads the entire JSON archive just to open one paper.

The local import contains 1,700 source-linked questions. Rule-based chapter tags now cover 540
questions; untagged records remain available in subject/year searches. Topic tagging is not proof
of exhaustive chapter coverage. Four Earth-interior-related questions were visually compared with
the stored original pages. Other text is explicitly marked as review pending, not silently verified.

`data/question_text_reviews.json` records the reviewed question's checksum. If its text, options,
passage or directions change, re-importing invalidates that review. Checking question text is separate
from checking its answer key: `is_verified` still controls whether an answer may be revealed as verified.

## 3. Retrieval and generation are different jobs

- An actual-PYQ request is parsed into year, CDS cycle, subject, chapter and optional search words.
  Common spelling errors such as “interiro earth” are normalized. Ambiguous requests ask for a subject.
- PostgreSQL applies year/cycle/subject filters. Chapter tags or conservative keyword matching narrow
  the results. The default is ten records; explicit counts and "all" return up to 50 per response.
  Larger archives keep their full matching count and offer the next page. "All" means all indexed
  matches, not every question UPSC ever asked. A shortage is disclosed, never filled with fake PYQs.
  Specific focuses such as volcanoes filter the actual question text within the broader Earth-interior
  chapter, so a volcano request does not return unrelated crust/seismic questions just sharing a tag.
- The service returns structured records: IDs, exact stored wording, options, provenance and review
  status. React renders those records directly. There is **no model call** that can rewrite these cards.
- “Only 2026” and “show next PYQs” use the latest structured conversation result, scoped to its owner.
- A new topic replaces the old chapter even inside the same GK paper. History combines ancient,
  medieval and modern tags; the current local archive has 45 matching history records, not a
  guaranteed exhaustive history collection.
- “Are you sure?” / “Are these all?” reports the last search's coverage and review status without
  rendering its cards again. The saved search snapshot still supports subsequent year/page filters.
- Ordinary subject questions and explanations do not inherit archive-listing intent just because
  they mention a chapter. “Explain the first one” passes the displayed record's full question,
  options and verification flags to the tutor (bounded to 24,000 characters of record context).
- "Give me 50 questions related to that topic" uses a separate, clearly labelled AI-generation path.
  Generic question-set requests mean practice; explicit "actual PYQs" still means archive lookup.
  An archive follow-up such as "show all" retains the archive filters. A new topic replaces them.
- The Explain button sends a question ID; the server reloads the actual record and passes that exact
  question to the tutor. Missing answer keys remain labelled as AI reasoning. Visual problems require
  the original diagram, not a guessed description.

The existing Qdrant/Gemini RAG system remains useful for general explanations. Exact PYQ listing uses
deterministic database retrieval instead: a similar vector match alone cannot prove exam provenance.
An empty result means “not found in our indexed papers”, not “UPSC never asked this”.
Fast archive responses are expected: they do not wait for a language model. Their wording is a
template populated with real database results. Concept explanations are generated by Gemini;
we do not add artificial typing delays to make database results look like AI generation.

### Counted practice sets (September 29 update)

Previously, the tutor inherited an archive-only refusal from conversation history, while the archive
displayed five records by default. Those are separate issues: retrieving real papers and generating
new practice must not share the same limitations or provenance labels.

`question_requests.py` distinguishes archive requests, new practice, and ordinary explanations.
`practice_sets.py` resolves the topic from the current request first, then conversational context.
An unspecified topic triggers a clarification that remembers the requested count.

For 50 questions, the server now requests the complete set in one generation call, instead of five
simultaneous/queued ten-item batches. This reduces rate-limit pressure and gives the model one shared
context for diverse questions. A JSON schema specifies the exact question count, four options and a
valid integer answer index. Pydantic additionally checks distinct options, prompt/explanation lengths
and types. Exact normalized duplicate prompts are removed; at most two repair calls of up to 25 items
can fill missing items. This is structural validation, not a guarantee that every answer is correct
or that differently worded questions test different concepts.

The configured preferred model is still used first. `GEMINI_FALLBACK_MODEL` defaults to the tested
`gemini-3.5-flash-lite`; 2.5 Flash remains a final legacy fallback. A working model is reused, and
failed/throttled models have a shared per-worker cooldown so repair calls do not immediately hammer
the same unavailable endpoint. Keys and billing settings are unchanged.

The response reports requested and actual counts. Provider outages can produce a clearly disclosed
partial set; zero valid questions yields a retryable error. No templates pad the count. Generated
answers have explanations but are never labelled as an official answer key. Questions never enter
the PYQ bank and never acquire original-paper links.

Migration `20260929_15` adds `doubt_messages.practice_result` so the set is saved with its conversation.
The UI displays every returned item, numbered in order, with answers behind "Reveal answer &
explanation". The new answer scrolls to its beginning rather than skipping down to question 50.
Follow-ups can refer to a numbered question, including Q50. Normal subject questions still use the
general tutor/RAG path, even after an archive or practice discussion.

Large sets have a 150-second processing ceiling and a 165-second account lease; ordinary requests
retain 75/90 seconds. The cap is 50 questions per request. A large set can therefore take much longer
than a direct database lookup. This is real generation, not an artificial delay or a fixed question list.

Verification on September 29: the expanded regression suite covers 50-item generation, partial-set
repair, cooldowns, persistence, numbered follow-ups, command typos, polite pagination and topic switches.
Frontend lint, TypeScript, eight frontend tests and production build passed. A live generation check
returned 50 distinct volcano practice questions in 25.1 seconds with the new fallback. A later localhost
API check returned 48 and subsequent bulk calls hit transport/rate-limit failures; reliable full-set
delivery through the running API remains unverified. Strict-schema generation was verified live for
two questions, and 50-item schema/count enforcement is covered by mocked tests. Provider outages
can still produce explicitly labelled partial results or retryable errors. Ordinary lessons no longer substitute irrelevant paper excerpts when
generation fails, and "not a paper question" does not trigger paper-catalog retrieval.

The UI puts archive/practice/AI labels above each answer. After 12 seconds it shows real elapsed waiting
time, without fake tokens or progress percentages. Previous-paper tags and original links are preserved.

## 4. How the robot moves

The companion is procedural Three.js geometry, not a video or static picture. Head, eyes, arms,
body and book are separate objects. An animation state selects Wave, Read, Jump or idle.

- Reading reveals a real open book, rotates a hinged page, lowers the head and moves the arms.
- Jumping changes vertical position over a sine curve, adds slight body squash and adjusts the shadow.
- Blinking scales the eyes briefly closed; smiling and head movement respond to state.
- Waiting for an answer triggers reading; answer completion triggers a short jump.
- There are no Wave / Read / Jump controls. A 22-second visible-time routine waves, rests, reads
  and turns pages, rests, jumps and rests again. Actions start roughly every few seconds, with
  quiet intervals so the companion does not constantly demand attention. Clicking it still waves.
- Answer/loading reactions temporarily take priority over the automatic routine. A hidden tab or
  offscreen companion pauses its animation clock; reduced-motion disables the automatic routine.

Rendering is capped around 30 fps, pauses offscreen/in a hidden tab, and respects reduced-motion.
WebGL resources are disposed on unmount. A vector fallback remains if WebGL is unavailable.

## 5. Running and extending this work

From `Backend`:

```powershell
.venv\Scripts\python.exe -m alembic upgrade head
.venv\Scripts\python.exe scripts/import_question_bank.py
.venv\Scripts\python.exe scripts/import_question_bank.py --apply
.venv\Scripts\python.exe -m pytest tests -q
```

The first import is a dry run. Run the applied import before deploying the new frontend, and restart
the backend. Re-import after adding or correcting source transcriptions; unchanged entries are retained.
The importer needs the repository's existing frontend source JSON and paper images, only at import time.

From `Frontend/abhyaas`:

```powershell
node --experimental-strip-types --test tests/companion-motion.test.mjs
npm run lint
npm run build
```

Next priorities: review more transcriptions and chapter tags; import older official papers with
traceable provenance; expand chapter aliases; add a review interface and retrieval evaluation set.
For a much larger bank, replace streaming keyword scans with indexed full-text/topic tables; use
semantic search to suggest candidates, never to manufacture question text or exam citations.
Personalization continues to remember study preferences. It does not train model weights or turn
unreviewed student messages into trusted reference material.
